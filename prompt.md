# Hermes Gauntlet: Photorealistic Procedural Jungle Exploration

Build a first-person exploration game in **Three.js**.

The goal is not to make something that merely resembles a jungle game. The goal is to make the rendered experience look and feel like **photorealistic documentary footage of a real dense tropical jungle**, while remaining entirely procedural.

The finished experience should be a quiet, atmospheric first-person walk along a single winding jungle trail that eventually reaches ancient stone ruins and a large waterfall.

There is **no combat, no enemies, no weapons, no inventory, no UI, no HUD, and no game-like objectives**.

The player simply walks forward and experiences the environment.

## Absolute Constraints

* Use **Three.js**.
* Generate **everything procedurally in code**.
* **Zero external assets.**
* No downloaded textures.
* No downloaded models.
* No external vegetation libraries.
* No premade HDRIs.
* No external sound files.
* No external environment maps.
* No stock imagery.
* No asset packs.
* No procedural asset generated outside the project and imported afterward.
* Every mesh, texture, material, particle system, environmental effect, and sound must be generated by code.
* Do not fake the environment with a flat background image or panoramic image.
* The world must be genuinely 3D and explorable.
* Maintain a first-person camera.
* The player follows one continuous winding trail.
* Prioritize visual realism over gameplay mechanics.

## CRITICAL GAUNTLET RULE

Work on **exactly ONE system at a time**.

**DO NOT parallelize the systems.**

Do not fan out multiple implementation agents.

Do not ask multiple agents to build different systems simultaneously.

The machine running this project has limited resources, so the workflow must be strictly sequential.

For every system:

1. One implementation agent builds the system.
2. Render/run the current build.
3. Spawn **ONE separate visual-critic sub-agent**.
4. The critic must be a different agent from the implementation agent.
5. The critic must evaluate the rendered result against **real jungle photography/documentary footage**, not against other game environments.
6. The critic must inspect the rendered output only.
7. **Do not give the critic access to the implementation code.**
8. The critic must be extremely harsh.
9. The critic must identify anything that makes the scene look synthetic, procedural, low-quality, repetitive, or recognizably like a video game.
10. If the critic does not believe the system is convincingly photorealistic, iterate on that SAME system.
11. Re-render it.
12. Spawn a fresh separate critic.
13. Repeat until the critic gives a genuine pass.
14. Only then proceed to the next system.

Do not accept "good enough."

Do not move to the next system because the scene is merely functional.

Do not allow one system's weakness to be excused because a later system might improve it.

Each system must individually reach a convincing visual standard before the next system begins.

Use the equivalent of:

`/loop`

for every system until it passes its visual-quality gate.

## Visual Quality Standard

The target is:

**"Could this frame plausibly be mistaken for real tropical-jungle documentary footage?"**

Not:

* "Does this look like a good Three.js demo?"
* "Does this look like a nice game?"
* "Does this look realistic for a browser game?"
* "Is this technically impressive?"

Those standards are too low.

The critic should specifically look for:

* repeated geometry
* obvious procedural patterns
* cloned trees
* identical leaves
* uniform spacing
* unrealistic foliage density
* overly clean surfaces
* overly saturated greens
* flat materials
* plastic-looking leaves
* perfectly uniform moss
* tiled textures
* visible texture repetition
* unrealistic scale
* insufficient micro-detail
* floating vegetation
* vegetation intersecting unnaturally
* unnatural tree growth
* perfectly vertical vegetation
* artificial lighting
* game-like fog
* incorrect atmospheric perspective
* flat shadows
* unrealistic ambient occlusion
* excessive sharpness
* lack of moisture
* lack of surface variation
* sterile ground
* unnatural rocks
* obvious polygonal silhouettes
* unrealistic water
* repeated particle patterns
* fake-looking mist
* unrealistic waterfall behavior
* excessive bloom
* unnatural color grading
* lack of depth
* anything that immediately reveals "computer-generated game environment"

The critic should compare the visual result mentally against **real tropical rainforest photography**, including close-up vegetation, forest trails, wet rocks, moss, canopy lighting, mist, ruins, and waterfalls.

## Environment Composition

The complete journey should follow this progression:

### Stage 1 — Dense Jungle Entrance

The trail begins inside dense tropical vegetation.

The canopy should be heavy enough that sunlight is partially obscured.

The player should immediately feel surrounded by vegetation.

Include:

* large tropical trees
* tangled roots
* vines
* ferns
* broad leaves
* smaller ground plants
* fallen branches
* leaf litter
* moss
* damp soil
* rocks
* subtle puddles
* organic debris

The vegetation should not appear arranged by a grid or repeated procedural pattern.

### Stage 2 — Narrowing Trail

The path gradually becomes narrower and more enclosed.

Vegetation should encroach naturally on both sides.

The canopy should create changing patches of light and shadow.

The player should gradually begin hearing more distant water.

The environment should subtly communicate that the waterfall is getting closer without explicitly telling the player.

### Stage 3 — Ancient Ruins

The jungle eventually opens into a clearing containing ancient stone ruins.

The ruins should feel genuinely old and abandoned.

They should be:

* partially collapsed
* irregular
* weathered
* covered with moss
* covered with vines
* stained by moisture
* eroded
* cracked
* partially buried
* integrated into the surrounding jungle

Avoid clean modular-looking temple pieces.

Avoid perfectly symmetrical ruins unless naturally appropriate.

The ruins should look as though they have existed in this environment for centuries.

### Stage 4 — Waterfall Reveal

Behind the ruins is a cliff face with a large waterfall.

The final clearing should provide a strong visual reveal.

The waterfall should descend from the cliff into a pool/river system.

Include:

* flowing water
* turbulence
* mist
* splash
* wet rocks
* wet vegetation
* water droplets
* spray catching light
* river movement
* damp surfaces
* atmospheric perspective

The waterfall should feel integrated into the environment rather than pasted onto it.

# SYSTEM ORDER

The systems MUST be completed in this exact order.

Do not reorder them.

## SYSTEM 1 — Terrain and Path Geometry

Build only:

* terrain
* ground
* elevation
* slopes
* cliffs
* rocks relevant to terrain
* riverbed foundations
* winding trail
* environmental scale
* spatial layout

Create a convincing continuous jungle path leading toward the final ruins/waterfall location.

The path should feel naturally formed rather than like a spline placed on a plane.

Use procedural variation to avoid obvious repetition.

### Gate

Spawn one separate harsh visual critic.

The critic evaluates only the rendered result.

If the terrain/path looks artificial, flat, repetitive, game-like, or obviously procedural:

**iterate on System 1.**

Do not proceed until it passes.

---

# SYSTEM 2 — Vegetation

After System 1 passes, add:

* trees
* branches
* roots
* vines
* ferns
* bushes
* broadleaf plants
* grasses
* ground cover
* fallen vegetation
* leaf litter
* moss
* organic debris

Use procedural variation aggressively.

Trees should not be clones.

Vegetation should vary in:

* size
* rotation
* curvature
* branching
* density
* species-like appearance
* age
* health
* orientation
* clustering

Vegetation should respond naturally to the terrain and trail.

Avoid evenly distributed vegetation.

Create believable ecological density gradients.

### Gate

Spawn a DIFFERENT harsh visual critic.

The critic sees only the render.

If vegetation looks like repeated primitives, low-poly foliage, procedural scatter, or game-engine vegetation:

**iterate on System 2.**

Do not proceed until it passes.

---

# SYSTEM 3 — Lighting and Atmosphere

Add:

* realistic sun illumination
* canopy shadowing
* volumetric-looking light
* god rays
* atmospheric depth
* jungle humidity
* mist
* subtle airborne particles
* ambient occlusion
* realistic shadow behavior
* light variation beneath canopy

Sunlight should penetrate the canopy in irregular shafts.

Do not make the entire scene uniformly bright.

The atmosphere should become more humid and visually dramatic around the waterfall.

### Gate

Spawn a DIFFERENT harsh visual critic.

If lighting resembles a game-engine preset, generic fog, flat ambient lighting, or artificial volumetric effects:

**iterate on System 3.**

Do not proceed until it passes.

---

# SYSTEM 4 — Stone Ruins and Temple Geometry

Add the ancient ruins.

Every stone element must be procedurally generated.

Include:

* stone blocks
* broken walls
* columns
* steps
* platforms
* partially collapsed structures
* cracks
* erosion
* moss
* vines
* dirt accumulation
* weather staining

Avoid clean repeated modular assets.

Stone should have irregular geometry and surface variation.

The ruins must look physically integrated with the terrain and vegetation.

### Gate

Spawn a DIFFERENT harsh visual critic.

If the ruins look like a generic procedural temple, game asset pack, clean blockout, or repeated geometry:

**iterate on System 4.**

Do not proceed until they convincingly resemble genuinely ancient ruins photographed in a jungle.

---

# SYSTEM 5 — Waterfall and Water

Add:

* river
* stream
* waterfall
* pool
* water surface variation
* turbulence
* foam
* splash particles
* spray
* wet rocks
* wet vegetation
* water reflections
* water refraction-like effects where feasible
* moisture accumulation

The waterfall must have believable vertical flow and turbulence.

Water must interact visually with surrounding surfaces.

The area immediately around the falls should be visibly wetter than the rest of the jungle.

### Gate

Spawn a DIFFERENT harsh visual critic.

If the water looks like a scrolling texture, transparent plane, particle wall, or obvious game effect:

**iterate on System 5.**

Do not proceed until the waterfall feels physically convincing.

---

# SYSTEM 6 — Procedural Sound Design

Generate all sound procedurally in code.

No external audio files.

Create an evolving jungle soundscape containing:

* distant birds
* nearby birds
* insects
* subtle wind
* leaves
* branches
* distant water
* increasingly prominent water
* waterfall roar
* splash
* environmental ambience

Sound should change naturally based on player position.

As the player approaches the waterfall:

* water becomes louder
* splash becomes more prominent
* nearby jungle ambience remains present
* distant environmental sounds become appropriately masked

Avoid repetitive loops that immediately reveal themselves as synthesized game audio.

Use procedural synthesis, filtering, modulation, spatialization, and layered variation where possible.

### Gate

Spawn a DIFFERENT harsh critic.

The critic evaluates the audiovisual result, particularly whether the soundscape feels like a real environment rather than looping game ambience.

If it sounds repetitive, synthetic, empty, or disconnected from the scene:

**iterate on System 6.**

---

# SYSTEM 7 — Post-Processing and Final Polish

Only after every previous system has passed should you add:

* color grading
* tone mapping
* subtle bloom where physically justified
* depth of field
* motion characteristics
* exposure refinement
* contrast refinement
* atmospheric perspective
* subtle lens characteristics
* final visual cohesion

Do not use post-processing to hide weak geometry.

Post-processing is the final layer, not a substitute for realism.

Avoid the typical "cinematic game filter" look.

The goal remains:

**real documentary footage.**

### Final Gauntlet

Spawn a final independent visual critic who has NOT built the environment.

Give the critic only the rendered experience.

Have the critic evaluate the entire journey from beginning to waterfall.

The critic must answer:

1. Does this look like a real tropical jungle?
2. Does the vegetation look physically believable?
3. Does the terrain look natural?
4. Do the ruins look genuinely ancient?
5. Does the waterfall look physically convincing?
6. Does the atmosphere resemble real humid jungle conditions?
7. Does the lighting resemble real-world tropical lighting?
8. Are there obvious procedural repetitions?
9. Are there obvious game-engine artifacts?
10. Does anything immediately break the illusion?
11. Does the experience feel like a nature documentary rather than a game?

If the answer to any major category is no:

**continue iterating.**

Do not declare completion.

---

# Performance Constraint

The experience must remain interactive.

Do not solve realism by blindly multiplying geometry until the browser becomes unusable.

Prefer intelligent procedural techniques such as:

* instancing
* level-of-detail strategies
* procedural batching
* efficient particle systems
* shader-based detail
* generated textures
* distance-based complexity
* selective high-frequency geometry
* frustum culling
* efficient vegetation representation

The target is the strongest visual result that can remain playable in Three.js.

---

# Agent Discipline

This is a sequential Gauntlet.

At no point should multiple implementation agents work simultaneously.

For each system:

**IMPLEMENT → RENDER → CRITIC → ITERATE → CRITIC → PASS → NEXT SYSTEM**

The implementation agent and critic must always be separate.

The critic must never receive the source code.

The critic judges the actual rendered result.

Never let the implementation agent grade its own work.

Never skip a critic cycle.

Never mark a system complete simply because the implementation technically works.

---

# Definition of Done

The project is finished only when:

* all seven systems have individually passed their visual gates
* the complete trail is playable from beginning to waterfall
* the scene contains no external assets
* all meshes are procedural
* all textures/material detail is procedural
* all sounds are procedurally generated
* there is no combat
* there is no HUD
* there is no UI
* there are no artificial objectives
* the environment feels cohesive
* the waterfall reveal feels rewarding
* the ruins feel ancient and naturally embedded in the jungle
* vegetation does not look cloned or repeated
* lighting feels physically plausible
* atmosphere feels humid and volumetric
* water feels integrated into the environment
* sound evolves with player position
* the final result does not immediately read as a generic Three.js demo

The ultimate quality test is:

> If a viewer saw the rendered footage without knowing it was generated in Three.js, would they reasonably mistake it for footage captured inside a real tropical jungle?

If not, **do not stop.**

Continue the Gauntlet loop until the answer is genuinely yes.

Do not optimize for finishing.

Optimize for **breaking the illusion of "video game" and replacing it with the feeling of "real place."**


# GitHub Checkpoint Protocol

GitHub checkpointing is a mandatory part of the Gauntlet workflow.

The repository is the persistent checkpoint history for the project.

## Checkpoint Rule

After a system has successfully passed its independent visual-critic gate:

1. Verify the project runs successfully.
2. Verify the current system is actually present in the working build.
3. Review the git diff.
4. Stage the relevant project files.
5. Create a git commit for that completed system.
6. Push the commit to the configured GitHub remote.
7. Confirm that the push succeeded.
8. Only after the GitHub checkpoint succeeds may the workflow advance to the next system.

Never advance to the next system before successfully creating the checkpoint.

## Commit Naming

Use clear checkpoint commit messages:

* `checkpoint: system 1 - terrain and path`
* `checkpoint: system 2 - vegetation`
* `checkpoint: system 3 - lighting and atmosphere`
* `checkpoint: system 4 - stone ruins`
* `checkpoint: system 5 - waterfall and water`
* `checkpoint: system 6 - procedural sound`
* `checkpoint: system 7 - post processing and polish`
* `checkpoint: final - photorealistic jungle gauntlet passed`

## Failed Iterations

Do NOT create a GitHub checkpoint for every failed critic iteration.

Failed iterations should normally remain local while the current system is being improved.

Only checkpoint a system after the independent critic gives PASS.

If useful for debugging, local commits may be created during development, but they should not be pushed as official Gauntlet checkpoints.

## Checkpoint Integrity

Every official checkpoint must represent a working state.

Never push:

* broken builds
* incomplete systems
* placeholder implementations
* known failing critic states
* half-finished system transitions

If a system passes visually but the application is broken, fix the build before creating the checkpoint.

## Git Safety

Before committing:

* inspect `git status`
* inspect the relevant `git diff`
* ensure generated junk, secrets, credentials, API keys, environment files, node_modules, build caches, and other unnecessary files are not committed
* respect the project's `.gitignore`

Never commit secrets.

Never commit `.env` files containing credentials.

Never expose API keys, tokens, passwords, or private credentials in the repository.

## Push Failure

If the commit succeeds but the GitHub push fails:

1. Do NOT proceed to the next system.
2. Diagnose the push failure.
3. Fix the GitHub synchronization problem if possible.
4. Retry the push.
5. Only proceed after the checkpoint is confirmed on the remote repository.

Do not discard completed work because a push failed.

## Recovery

The GitHub checkpoints must make it possible to recover the project to the last successfully completed system.

Each checkpoint should therefore leave the repository in a coherent, runnable state.

The intended recovery points are:

`system-1 → system-2 → system-3 → system-4 → system-5 → system-6 → system-7 → final`

## Mandatory Workflow

The complete workflow is:

BUILD
→ RENDER
→ INDEPENDENT CRITIC
→ FAIL
→ ITERATE
→ RENDER
→ INDEPENDENT CRITIC
→ ...
→ PASS
→ VERIFY BUILD
→ GIT STATUS
→ GIT DIFF
→ COMMIT
→ PUSH TO GITHUB
→ CONFIRM REMOTE CHECKPOINT
→ NEXT SYSTEM

Never skip the GitHub checkpoint between systems.
